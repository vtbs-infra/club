# B站集成

Club 通过三个适配器边界连接 B站：

| 接口                   | 用途                             |
| ---------------------- | -------------------------------- |
| `LiveMessageSource`    | 接收验证直播间消息，证明用户 UID |
| `CreatorProfileSource` | 读取主播显示名称和规范直播间     |
| `GuardRosterSource`    | 获取主播月度大航海名单           |

应用固定装配公开 Web 实现；测试从 `tests/helpers` 显式注入替身，不通过环境变量切换。

公开 Web 接口可能随 B站调整而变化。Provider 原始结构只存在于适配器内部，业务模块
使用 Club 规范化后的类型。

## 平台读取账号

平台管理员在“B站集成”页面扫码登录一个 B站读取账号。这个账号供三个适配器共同使用，
普通用户注册和找回仍使用自己的 UID 验证，不需要把自己的 B站登录凭据交给 Club。

登录流程是：申请二维码 → 手机扫码确认 → 服务端核对账号 → 管理员点击“启用此账号”。
页面展示候选账号昵称、头像和 UID；未明确启用前，原有效账号继续承担读取。
二维码和候选账号绑定发起管理员的当前 Club 会话，刷新页面可继续，退出或撤销会话后不能启用。
二维码最长有效三分钟，扫码成功后候选凭据最多保留五分钟；取消、过期、失败或启用后清除任务秘密。

`passport-client` 实现 BiliTV 签名协议及有界 HTTPS 请求，登录和续期参考
[biliup](https://github.com/biliup/biliup)，不依赖其程序运行。扫码结果的 token UID、Cookie 中的
`DedeUserID` 和 Web 登录查询必须一致。账号凭据只发送到固定 B站服务，不返回浏览器或写入日志。

`session-service` 在 PostgreSQL 的 `bilibili_sessions` 单槽保存加密凭据，在
`bilibili_login_attempts` 保存短期扫码任务。B站凭据使用独立的版本化 AES-256-GCM 密钥，
与地址加密分开配置，见[配置参考](../configuration.md)。

### 检查、续期与恢复

后台运行器每两秒处理到期任务；普通登录检查间隔为四小时，不因扫码轮询而反复查询登录状态。
明确的临时网络或风控拒绝保留凭据，稍后重试；确定失效或无法解密则提示重新扫码。
管理员可手动请求只读检查；续期只按登录协议的返回结果决定。

刷新前持久化操作标识和凭据版本，收到完整刷新结果后先加密保存，再核对身份并整体启用。
进程在保存后中断，可从已保存结果恢复检查；请求结果不明、或只留下过期的刷新意图时，
不自动重发旧刷新请求，而是要求重新扫码。数据库事务无法撤销 B站已经完成的 token 轮换。

启用、换号和断开使用版本与操作归属校验；迟到的旧请求不能覆盖新会话。
断开会清除本地凭据与候选任务，取消读取连接及在途请求，不代表退出用户其他 B站设备。
进程重启后先检查持久化登录态，通过后自动恢复启用房间的连接。

### 读取上下文

每次操作取得不可变凭据快照。设备 Cookie 初始化完成后，再覆盖该快照的登录 Cookie，
保证初始化不会冲掉登录态。只缓存完成的设备初始化结果，不共享由另一次请求控制的 Promise。
主播资料的多步查询与一次名单 Attempt 的全部分页分别固定同一快照。
账号换号、续期或断开会取消旧快照，旧名单 Attempt 失败后按现有流程处理，不拼接两版账号的分页。

## UID 验证

### 完整流程

1. 平台管理员扫码并启用读取账号，配置并启用验证直播间。
2. Club 为启用房间保持鉴权连接，收到 WebSocket 认证 `code=0` 后标记通道就绪。
3. 匿名浏览器创建注册或账号找回挑战，服务只向实际就绪的房间分配验证码。
4. Club 返回 `CLUB-` 加 10 位随机字符的验证码和直播间链接，数据库只保存 HMAC 摘要。
5. 用户使用自己的 B站账号发送验证码。
6. 适配器输出消息内容、实际发送者 UID、房间、时间和稳定事件 ID。
7. 身份验证服务检查消息并原子地将挑战标记为已验证。
8. 用户在原浏览器提交注册资料或新密码，事务消费证明并完成操作。

读取账号未就绪时返回 `BILIBILI_AUTH_REQUIRED`；没有可用的鉴权房间时返回
`VERIFICATION_CHANNEL_NOT_READY`。这些请求不生成一个等待建连的验证码。
注册请求不接受用户自行指定 UID 或直播间。账号找回在发起时指定目标 UID，消息必须属于该 UID。
等待验证与验证后提交各有十分钟有效期，详见[账号认证](../authentication.md)。

### 直播消息连接

`PublicWebLiveMessageSource` 使用 `bilibili-live-danmaku` 0.7.16 处理房间解析、弹幕 Token、
WebSocket 心跳及 zlib/Brotli 解压。Club 独立解析原始认证帧，不以依赖的 `CONNECT_SUCCESS`
事件名代替认证结果；支持协议 0/1 的认证 JSON，拒绝非零或畸形的认证响应。

连接步骤：

```text
读取已核验的账号快照 + 初始化设备 Cookie
  -> 解析直播间
  -> 使用同一登录态获取弹幕 Token
  -> 使用快照 UID 和设备 buvid 连接 WebSocket
  -> 核对认证 code=0
  -> 心跳与消息接收
```

发送者只取 `DANMU_MSG.info[2][0]` 或 `info[0][15].user.uid`；两者有效且冲突时丢弃。
缺失、为零、非法格式或不安全的数值 UID 都不能作为证明，不从昵称、勋章或用户哈希猜 UID。
消息时间取 `send_time` 或 `info[0][4]`，接受 Unix 秒/毫秒；无有效时间就丢弃，不以接收时间替代。
消息必须晚于挑战创建时间，保留一秒精度容差。事件 ID 用于幂等消费。

### 房间生命周期与诊断

启用房间在读取账号可用期间常驻连接，与待处理挑战数量无关。停用房间或会话失效后立即撤销
连接需求；断线按有上限的退避重连。连接建立的十五秒期限覆盖设备初始化到 WebSocket 鉴权。
关闭时取消建连和连通性测试，等待已经开始的消息处理完成后才能关闭数据库。

身份验证不再查询 `gethistory`，也不匿名回退。连接断开期间发送的弹幕可能丢失，用户应在
页面显示恢复后重发原验证码；期限不延长。已取得的 VERIFIED 证明继续按原期限使用。

后台分别展示账号有效性、上游可达性、运行操作和实际房间连接状态。鉴权成功并不代表已收到
真实 UID；房间单独显示最近收到可信 UID 消息的时间，无样本时明确显示“尚无真实 UID 弹幕样本”。
该记录仅表示解析到有效 UID 字段，完整验收仍应由与读取账号不同的账号发送消息并核对 UID。

缺失 UID、字段冲突、解码或处理失败按房间和原因限频记录，不保存无关弹幕正文。
成功验证记录消息年龄，便于区分上游传输延迟和 Club 处理耗时。B站业务不可用不会阻止正常
密码登录、管理员重新扫码及基础健康检查；后台运行器自身故障仍会影响 Readiness。

## 主播资料

注册主播前，普通用户必须在注册时通过直播间验证码验证 UID。平台把这个已验证 UID 交给
`CreatorProfileSource`，依次调用三个公开接口：

- `room/v1/Room/getRoomInfoOld?mid=<UID>` 查询账号的直播间别名；
- `room/v1/Room/get_info?room_id=<别名>` 查询规范房间号，并校验房间所属 UID；
- `live_user/v1/UserInfo/get_anchor_in_room?roomid=<规范房间号>` 查询昵称，再次校验主播 UID。

资料读取只依赖这些基础接口。规范化结果只有三个字段：

```json
{
  "biliUid": "<已验证 UID>",
  "displayName": "<B站当前昵称>",
  "roomId": "<规范直播间 ID>"
}
```

没有可用直播间、UID 不一致、空昵称或非法标识都会使注册或刷新失败。平台不接受手填值
替代 Provider 结果。注册后，主播或平台管理员可以显式刷新昵称与直播间；刷新只更新未来
且尚未开始的名单任务，已经执行或定稿的任务继续保留创建时冻结的主播信息。

生产应用使用公开 Web 资料适配器；测试显式注入确定性资料源。
资料、名单与直播适配器统一通过 `BilibiliReadingSession` 获取不可变登录快照；
业务服务不接触 Cookie、token 或登录协议字段。

## 月度大航海名单

### Provider 请求

`PublicWebGuardRosterSource` 调用：

```text
/xlive/app-room/v2/guardTab/topListNew
```

`GuardRosterSource.openCapture` 为一次 Attempt 固定读取账号，分页大小为 30。设备初始化、
全部分页和第一页复查共享 Attempt 取消信号与凭据版本；超时、换号或关闭会终止在途请求。

响应元数据：

| 字段        | 含义                            |
| ----------- | ------------------------------- |
| `info.num`  | 声明的成员总数                  |
| `info.page` | 声明的分页总数                  |
| `info.now`  | 当前页码                        |
| `top3`      | Provider 在各页重复返回的前三名 |
| `list`      | 其余成员                        |

第一页把 `top3` 加入一次，再追加 `list`；后续页面只处理 `list`。

### 成员规范化

| Provider 字段       | Club 字段      |
| ------------------- | -------------- |
| `uinfo.uid`         | B站 UID        |
| `uinfo.base.name`   | 抓取时显示名称 |
| `uinfo.guard.level` | 大航海等级     |
| `rank`              | 排名           |

等级映射：

| 原始值 | Club 等级  |
| ------ | ---------- |
| `1`    | `GOVERNOR` |
| `2`    | `ADMIRAL`  |
| `3`    | `CAPTAIN`  |

出现其他等级值时，整次抓取不会通过一致性校验。

## 分页一致性

Provider 没有返回服务端快照时间或一致性 Token。Club 将一次名单任务定义为有时间上限
的完整抓取区间：

1. 获取第一页并读取声明总数与页数；
2. 在发起后续请求前校验分页数、成员数和单页响应大小上限；
3. 使用有限并发获取全部声明分页；
4. 再次获取第一页；
5. 比较元数据和关键成员集合；
6. 规范化并验证完整成员列表。

以下情况会使尝试失败：

- 成员总数或分页总数变化；
- 复查第一页时关键成员发生变化；
- 缺页或页码顺序错误；
- UID 重复；
- 等级未知；
- 规范化成员数与声明总数不一致；
- Provider 声明的页数、成员数或单页响应超过安全上限；
- 抓取超过 120 秒。

只有通过完整一致性检查的尝试可以进入名单定稿流程。

## 原始证据

每个 Provider 原始响应按以下顺序处理：

1. 对原始字节计算 SHA-256；
2. 使用 gzip 压缩；
3. 原子写入对象存储。

对象路径：

```text
private/snapshots/{runId}/{attemptId}/page-{page}.json.gz
```

PostgreSQL 保存：

- 对象键；
- SHA-256；
- 原始与压缩字节数；
- 成员数量；
- 抓取时间；
- Provider 分页元数据；
- 每次抓取的规范化成员；
- 月度任务接受的抓取 ID，正式名单直接读取这份成员集合。

数据库和对象存储需要作为同一个备份集保存。

## 自动化测试

测试覆盖：

- 直播消息 Fixture 规范化；
- BiliTV 扫码、续期、身份一致性与有界响应；
- 真实发送 UID、事件时间与稳定事件 ID；
- 凭据加密、管理员会话绑定、并发替换和刷新崩溃恢复；
- 连接复用、失败隔离与重连；
- 挑战过期、重放、断线重发和进程重启；
- 名单 Fixture 规范化；
- 主播资料与规范直播间解析；
- 分页漂移、一致性和超时；
- 名单定稿与证据不可变约束。

名单 Fixture：

```text
tests/fixtures/bilibili/guard-roster-page.json
```

CI 在 B站边界显式注入 Fake 资料、名单和直播消息来源，不访问真实 B站服务。完整浏览器测试保留真实认证、HTTP、数据库和后台任务，不能证明当前 B站接口的可用性。

## Provider 变更处理

当房间认证、响应字段、压缩方式或风控行为变化时：

1. 在适配器内更新解析与连接逻辑；
2. 更新脱敏 Fixture；
3. 运行单元测试和 PostgreSQL 集成测试；
4. 使用非敏感直播间完成连接与名单测试；
5. 检查存储证据 SHA-256 和规范化成员数；
6. 部署后观察验证房间与名单任务状态。

业务服务、数据库和前端 API 类型不应直接引用 Provider 原始响应结构。
