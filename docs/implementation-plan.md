# Club 实施计划

> 状态：已定稿，待执行  
> 更新日期：2026-07-29

## 目标

本计划用于把 Club 收敛为可以承载真实领取与发货数据的稳定版本。现有 TypeScript
模块化单体、单应用实例、PostgreSQL、React 和本地对象存储继续保留；本轮工作不更换
技术栈，也不改变部署拓扑。

实施重点依次是：

1. 修复会改变资格、订单或冻结数据的正确性问题；
2. 让后台任务的实际运行状态可以被观察和判断；
3. 收拢服务端、Web 和 OpenAPI 之间的契约；
4. 简化过大的业务服务和前端页面；
5. 修复关键流程中的交互误导与错误反馈；
6. 删除没有实际用途的模型、依赖和运行时负担。

## 产品与数据不变量

后续实现必须同时满足以下不变量：

### 账号

- 账号身份只有 `USER`、`CREATOR` 和 `PLATFORM_ADMIN`；
- 一个账号在任一时刻只有一个身份；
- 普通用户通过平台启用的固定验证直播间绑定 B站 UID；
- 已提交礼物单中的账号、UID 和领取资料不会因后续解绑而改变。

### 月度名单

- 每个启用主播每个自然月都执行名单任务，与该月是否发布礼物无关；
- 计划时刻是主播配置时区当月最后一天 `23:59:00`；
- `capture_started_at` 在第一次 Provider 请求发出前持久化，并据此判断
  `ON_TIME` 或 `LATE`；
- 分页抓取完成并通过一致性校验后才能定稿；
- `LATE` 结果必须由平台管理员批准；
- 已定稿成员和证据不可修改；
- 同一个名单任务同一时刻最多只有一次有效抓取尝试。

### 礼物

- 主播可以不在某个月发布礼物；
- 同一主播、同一资格月份最多有一个有效发布；
- 已发布礼物与已定稿名单无论谁先出现，都能触发同一套幂等资格匹配；
- 同一名单成员只生成一张礼物单；
- 发布操作使用用户当前编辑的完整内容，不允许发布旧草稿。

### 地址与领取

- 地址簿是用户可新增、修改和删除的资料；
- 礼物单提交后保存独立加密地址快照；
- 删除或修改地址簿不会更新、置空或删除历史订单快照；
- 领取提交必须使用当前账号仍然有效的 UID 绑定。

### 发货

本计划采用“一张礼物单对应一次发货”的语义：

- 一张订单最多有一张有效运单；
- 创建运单后订单进入 `SHIPPED`；
- 该运单确认送达后订单进入 `COMPLETED`；
- 不保留表面支持拆分发货、实际由整单状态驱动的中间模型。

如果将来确实需要拆分发货，应作为独立功能重新设计包裹分配和聚合状态，不在当前状态
机上增加兼容分支。

## 实施约束

- 已存在的迁移文件保持不变，结构修复使用新迁移；
- 每次迁移都必须同时验证空数据库和从当前 Schema 升级；
- 不使用特殊数据修复分支掩盖错误的数据模型；
- 不为了拆文件引入 Repository 基类、Command Bus、事件总线或通用表单框架；
- 服务端业务错误继续使用稳定错误码；
- 后台错误必须被记录并进入状态模型，不允许无声吞掉；
- 每个阶段完成后恢复全部适用质量检查，再进入下一阶段；
- 本轮不引入 UI 主题与外观配置、多实例租约或手工名单入口。

## 执行顺序

```text
阶段一：核心数据与状态正确性
  -> 阶段二：Runtime 与健康状态
    -> 阶段三：共享契约与代码边界
      -> 阶段四：关键 UI/UX 工作流
        -> 阶段五：稳健性与无效复杂度清理
          -> 阶段六：文档、迁移和发布验收
```

前两个阶段以修复行为为主，避免同时进行大规模文件移动。第三阶段在业务语义稳定后完成
结构收拢，第四阶段再基于稳定契约修改前端，减少重复工作。

### 2.2 分离进程健康、技术就绪与业务配置

接口语义：

- `/health/live`：进程仍能响应；
- `/health/ready`：数据库 Schema、对象存储和关键 Runtime 已初始化；

- [ ] Runtime 未启动或长期无 Tick 时 readiness 失败；

- [ ] 零验证房间不应阻止管理员进入平台完成初始配置；
- [ ] Docker 健康检查根据部署语义选择 readiness，而不是只检查 live；
- [ ] 系统页展示最后成功、最近错误和下次重试时间。

### 2.3 修复消息与后台重试可靠性

- [ ] 直播历史事件只在数据库处理成功后标记为已消费；

## 端到端验收清单

整个计划只有在以下业务闭环全部成立后才算完成：

1. 平台管理员创建主播并配置至少一个验证直播间；
2. 普通用户注册后在该房间发送验证码并绑定正确 UID；
3. 多个主播在同一月末同时开始名单抓取，失败任务不阻塞其他主播；
4. 准时一致名单自动定稿，延迟一致名单等待管理员确认；
5. 主播没有发布礼物的月份只保存名单，不生成礼物单；
6. 礼物在名单前或名单后发布，都只为每位符合条件成员生成一张礼物单；
7. 用户可以使用默认地址直接领取；
8. 用户领取后删除地址簿记录，历史订单地址仍可由授权角色读取；
9. 主播发布的是当前编辑内容，而不是上次保存的草稿；
10. 主播为订单录入一张运单，用户查看物流，送达后订单完成；
11. Runtime 故障、缺少验证房间和未迁移数据库不会被误报为平台正常；
12. 普通用户、主播和管理员的核心流程在桌面与窄屏下都有明确反馈。
