# Creator-first rebuild plan

Status: approved for implementation  
Approved: 2026-07-29  
Baseline: `5387054`  
Implementation branch: `codex/creator-first-rebuild`

## 1. Why this rebuild exists

The current implementation exposes its tenancy and persistence model directly
to people using the product. Every authenticated account is sent to an
organization picker, recipient gifts are buried in the account page, and
creator workflows expose terms and identifiers such as campaign, snapshot,
entitlement, shipment key, and raw claim fields.

This rebuild replaces that product model. It is not a visual wrapper over the
existing organization APIs.

## 2. Approved product decisions

### Identities

The application has exactly three mutually exclusive account roles:

- `USER`: recipient-facing account;
- `CREATOR`: owns and operates exactly one creator profile;
- `PLATFORM_ADMIN`: manages the deployment and every creator.

There are no organizations, organization memberships, creator scopes, operator
accounts, fulfillment accounts, or combined roles in this version.

Public registration creates a `USER`. A platform administrator promotes an
existing account to `CREATOR` and creates its one creator profile. The initial
platform administrator continues to be created through the CLI.

### Roster capture and gifts

Roster capture and gift publication are independent:

- every active creator receives one immutable month-end roster snapshot each
  month whether or not that creator plans to send a gift;
- a creator may publish no gift for a month;
- a creator explicitly creates a gift release and selects its eligibility
  month;
- at most one gift release exists for one creator and eligibility month;
- publishing before roster finalization waits for the roster;
- publishing after roster finalization creates gift orders immediately;
- gift orders are generated only when both a published gift release and a
  finalized roster exist;
- a month with no published gift creates no draft warning, recipient card, or
  placeholder order;
- all reconciliation remains idempotent and there is no manual roster,
  eligibility, or gift-order grant path.

An unregistered recipient's order remains attached to the Bilibili UID. A user
who later proves that UID sees the historical order. Submitting an order freezes
the claimant, delivery address, and release-defined options.

### UI customization

All runtime UI customization is removed during this rebuild:

- deployment themes;
- appearance settings;
- page and block editors;
- draft/publish/versioned site pages;
- generic asset library and brand-image management;
- per-creator visual customization;
- `CLUB_UI_THEME`.

The rebuilt product has one fixed responsive visual system and one built-in
dashboard banner. Announcements, creator identity, and gift images are business
content rather than UI customization.

## 3. User-facing information architecture

### Recipient

Default route: `/dashboard`

Navigation:

- Dashboard
- Gift orders
- Announcements
- Account menu: Bilibili binding, delivery addresses, account, sign out

Dashboard order:

1. fixed banner;
2. five recent relevant announcements;
3. one contextual action when binding, address, expiry, or tracking requires
   attention;
4. gift-order cards.

Gift cards show creator, eligibility month, tier, gift, status, deadline or
tracking summary, and one primary action. Full address, phone, internal IDs,
snapshot terms, and shipment implementation details are not shown on cards.

Recipient states:

- `CLAIMABLE`: waiting to claim;
- `SUBMITTED` or `PROCESSING`: processing;
- `SHIPPED`: shipped;
- `COMPLETED`: completed;
- `EXPIRED`: expired;
- `CANCELLED`: cancelled.

Claiming is one continuous flow: gift review, existing or inline new address,
release-defined options, confirmation.

### Creator

Default route: `/creator`

Navigation:

- Overview
- Gift releases
- Gift orders
- Announcements
- Settings

Overview contains the next roster cutoff, latest roster result, active release
progress, order workload, pending shipments, and exceptions. The absence of a
gift release is never presented as an error.

A gift release editor selects an eligibility month and visually configures
tier packages, highest-only or cumulative behavior, gift images, claim dates,
and form fields. No DSL, package IDs, entitlement IDs, or shipment keys are
visible.

Creators process and ship their own orders. Shipment identifiers used for
idempotency are generated by the application.

### Platform administrator

Default route: `/admin`

Navigation:

- Overview
- Creators
- Roster sync
- Verification
- Platform announcements
- System

The administrator promotes creator accounts, configures creator Bilibili
identity and timezone, monitors aggregate roster results, handles late or
failed captures, manages verification rooms, and inspects system health.
Raw-page evidence is an exception-detail concern and is not part of creator
navigation.

## 4. Target domain model

Keep or rebuild around:

- `users`, `sessions`, `accounts`, `verifications`;
- `creators`;
- `bilibili_bindings`, binding challenges and verification rooms;
- roster snapshot runs, attempts, pages, candidates, and finalized members;
- `gift_releases`;
- release packages, items, tier rules, and form fields;
- `gift_orders` and `gift_order_items`;
- encrypted addresses and frozen order-address snapshots;
- shipments and shipment events;
- platform and creator announcements;
- audit logs.

Remove:

- `organizations`;
- `organization_members`;
- `member_creator_scopes`;
- every `organization_id`;
- organization announcement scope;
- appearance and site-content tables;
- the old organization, campaign, entitlement, claim, appearance, and
  site-content public contracts.

`creators.user_id` is unique and non-null. Creator-facing API calls resolve the
creator from the authenticated session and never accept a browser-supplied
creator ID. Administrator APIs use explicit creator IDs.

`gift_orders` are the primary business aggregate. They replace the exposed
entitlement-plus-claim model and are unique by gift release and finalized
roster member. Order items represent the tier packages earned under the
release's highest-only or cumulative rule.

## 5. Target API and web routing

API namespaces:

- `/api/v1/me/*`
- `/api/v1/creator/*`
- `/api/v1/admin/*`

Web routes:

- `/`, `/login`, `/register`;
- `/dashboard`;
- `/gifts`, `/gifts/:giftOrderId`;
- `/announcements`;
- `/account`, `/account/bilibili`, `/account/addresses`;
- `/creator`, `/creator/releases`, `/creator/releases/:releaseId`;
- `/creator/orders`, `/creator/orders/:giftOrderId`;
- `/creator/announcements`, `/creator/settings`;
- `/admin`, `/admin/creators`, `/admin/rosters`;
- `/admin/verification`, `/admin/announcements`, `/admin/system`.

Old `/organizations/*`, `/claims/*`, `/platform/site`, and
`/platform/appearance` routes are deleted rather than redirected through a
compatibility layer.

## 6. Implementation approach

This repository is pre-release. At approval time the local database contains
one administrator and no organizations, creators, releases, snapshots, claims,
or shipments. Do not build a legacy-data compatibility architecture.

Implementation is one target-state cutover:

1. write this approved context and update normative product documentation;
2. replace the schema and migration baseline;
3. rebuild role guards and creator resolution;
4. preserve and adapt Bilibili verification and immutable roster capture;
5. implement gift-release and gift-order aggregates;
6. implement recipient, creator, and administrator APIs;
7. replace all three web shells and flows;
8. delete obsolete modules, routes, assets, tests, documentation, and config;
9. rebuild the local Compose database and recreate the administrator;
10. run the full static, unit, integration, build, and browser acceptance gates.

No intermediate organization compatibility route or dual data model may remain
after the cutover.

## 7. Required acceptance

- The repository contains only the three approved roles.
- A recipient lands on the dashboard and sees the banner, recent news, and
  gift orders without selecting a workspace.
- A creator owns exactly one creator profile and cannot address another
  creator through creator APIs.
- A platform administrator can promote an account and configure that creator.
- Every active creator receives monthly immutable roster snapshots.
- Months without a gift release create no order and no missing-gift warning.
- Publishing against a finalized historical roster creates orders.
- Publishing before finalization produces the same orders after finalization.
- Late registration and UID binding reveal historical unclaimed orders.
- Claiming freezes address and options; later address-book changes do not alter
  the order snapshot.
- Shipment transitions cannot bypass the order state machine.
- No manual roster, eligibility, or gift-order creation path exists.
- Organization, theme, appearance, page-editor, generic site-content, and
  runtime UI-customization code is absent.
- Recipient claiming and tracking work on mobile-width layouts.
- Cross-role and cross-creator authorization tests pass.
- Formatting, linting, TypeScript, unit, integration, production build, and
  end-to-end tests all pass in the supported runtime.
